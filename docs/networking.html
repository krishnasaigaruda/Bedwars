How BlockWars Connects

BlockWars is a multiplayer Bedwars game that runs in a browser tab, with no game server of our own. This page walks through how two players' browsers find each other, talk to each other, and stay in sync. Plain-language first; the networking names come after.

1. The problem in plain words

Two friends open the game on two computers. One clicks Private Room and gets a code like ABCDE. The other types the code and clicks Join. A second later they're standing in the same lobby.

For that to work, three things have to happen:

  1. Find each other. The joiner only knows a 5-letter code. Something has to turn that code into "the browser on your friend's laptop".
  2. Open a line between them. Home routers block strangers from connecting in, so the two browsers need a trick to get a line open.
  3. Agree on what's happening. Both screens must show the same blocks, the same health and the same winner, even though messages take time to travel.

The rest of the page covers those three in order.

2. The phone-call picture

The easiest way to think about it is a phone call:

Phone book
A public server that maps a name to an address. You look your friend up, then hang up on the phone book. In our game this is PeerJS's free cloud server.
The call
A direct line between the two browsers. All game traffic goes over it; the phone book is no longer involved. Browsers have this built in, called WebRTC.
"What's my number?"
Your laptop doesn't know its own public address (the router hides it). A tiny helper server tells it. That's a STUN server; we use Google's free one.
Middleman
When the routers refuse a direct call, both sides call a relay that passes messages along. That's a TURN server. It's optional and needs an account (free relays have all shut down).
who talks to whom

Grey arrows (1, 2) are short setup calls. Green (3) is the normal path, browser to browser. Red dashed is the relay, used only when routers block the direct line.

3. Joining a room, step by step

Here is the exact order of messages when someone types a code and clicks Join. Before WebRTC can open a line, both sides must swap a description of themselves (what they want to send) and a list of possible addresses. They swap these through the phone book; that swapping is called signaling.

join sequence
Offer / answer
Each side's description of the connection it wants. The formal name is SDP; you never edit it by hand, the browser writes it.
Candidates
Possible addresses to reach a browser: its address on the home network, its public address (learned from STUN), and a relay address (from TURN, if one is set up).
ICE
The browser's process of trying candidate pairs until one gets through. If none do, the join fails. The game then shows which addresses each side offered so you can see why.

Steps 1–6 are why a typo shows "No room with code ABCDE": the PeerJS server answers step 3 with "nobody has that id". If steps 3–7 work but step 8 doesn't, the room exists but the routers won't let the line open.

4. One browser is the referee

Once connected, who decides what happened? If both browsers ran their own copy of the rules, they'd disagree: "I hit you first" on one screen, "No, I did" on the other. So one browser, the host, runs the real game. Everyone else sends what they did and draws what the host tells them. This is called a host-authoritative setup.

architecture

There's one exception to "the host decides everything": your own movement. Waiting for the host before you could walk would feel awful, so your browser moves you straight away and tells the host where you are. The host trusts it, within limits. This is called client-side prediction.

5. Two channels: safe and fast

The line between two browsers can carry more than one channel. BlockWars opens two, because messages fall into two kinds:

Safe channel
Every message arrives, in order. Used for things that must never be lost: placing a block, a hit, buying, chat, fall damage. Formally: reliable, ordered.
Fast channel
Like a radio: a message that gets lost is simply skipped. Used for positions and snapshots, which are sent 20 times a second, so a newer one is always on its way. Formally: unreliable, unordered, like UDP.

Why not send everything safely? On the safe channel, one lost packet holds up everything behind it until it's resent. On patchy Wi-Fi that showed up as other players freezing for half a second, then jumping. On the fast channel a lost position just means the next one is used.

one lost packet, two channels

Because fast messages can arrive out of order, each one carries a number (sq from joiners, the game tick time from the host). Anything older than the newest one already seen is thrown away.

6. Drawing other players smoothly

Positions arrive 20 times a second, but the screen redraws 60 or more times a second, and the arrivals are uneven. If we drew each player exactly where their last message said, they'd stutter.

So each other player is drawn about two ticks (100 ms) in the past, sliding smoothly between the two updates on either side of that moment. If updates stop for a moment, the player keeps moving the way they were for up to 3 ticks, then waits. This is interpolation (and, for the short guess, extrapolation). The code lives in render/remote.js.

playback runs behind the newest update

7. When it doesn't connect

Most of the time step 8 (ICE) finds a direct path: either both browsers are on the same home network, or STUN helps them punch through their routers. Some routers and firewalls can't be punched through. Then only a TURN relay can connect them.

The free public relays (Open Relay, PeerJS's own, freeturn.net) have all stopped answering. The TURN list in src/net/transport.js still names Open Relay, in case it comes back, but today it connects nothing. To get a working relay, add credentials from a free account (for example metered.ca or expressturn.com) to that list. Press F3 in game to see whether your connection is (direct) or (relay).

Other safety nets in the code:

  1. If the host's link to the PeerJS server drops, it reconnects, so the room code keeps working.
  2. When a page closes, it hangs up properly, so others see "left the game" at once.
  3. A connection that goes silent for 8 seconds is treated as gone, so no "ghost" players linger in the lobby.
  4. A failed join shows a report: whether the host answered, which steps ICE went through, and which kinds of address each side offered.

8. Starting a game

The host's browser also runs the lobby, so it decides when a game starts. One rule covers every online game: once there are enough players, a countdown starts by itself.

Private roomCountdown of 2 minutes once a second player joins. The host can press Start now (or Enter) to skip to the last 5 seconds.
Public gameCountdown of 30 seconds once two teams' worth of players are in. No one has a Start button: like Bedwars on a Minecraft server, there is no host to control it.
Someone joinsThe countdown goes back up to its full length so they can get ready (unless the host of a private room already pressed Start).
Room is fullThe countdown drops to 10 seconds.

Code: lobbyChanged(), join() and requestStart() in net/session.js; canStart() in main.js.

9. Voice chat rides the same line

Joiners only have a line to the host, never to each other. So voice works like a conference call: each joiner calls the host with their microphone, and the host's browser mixes everyone else's voices into one stream and sends it back. The host also works out who's talking from how loud each voice is, and tells everyone. Code: net/voice.js.

net/voice.jsVoice hub on the host, voice call on each joiner.
game/sim.jsThe real game rules, run only by the host. Joiners keep a "shadow" copy for drawing.
render/remote.jsOther players: interpolation buffer and playback clock.
main.jsGlues it together: sends your position every tick, applies snapshots, handles events.
